# Data Cleaning — "How Mid Am I?"

This document explains how the raw Ironman CSVs become the analysis-ready
`clean_results` table, and **why** each cleaning decision was made.

## Transparency model

Two kinds of information live in two different places, on purpose:

| | Where | Who produces it |
|---|---|---|
| **The numbers** (counts, % removed, coverage) | [`data/cleaning_report.json`](../data/cleaning_report.json) | generated by `scripts/clean_data.py` on every run — **never hand-typed** |
| **The rationale** (why each rule exists) | this document + comments in `scripts/clean_data.py` | written by hand |

The figures quoted below were taken from the generated report. If a threshold
changes, re-run the cleaner and the JSON updates itself — the prose explains the
*why*, the JSON is the source of truth for the *how much*. They cannot silently
disagree, because there is only one place the numbers come from.

> **Audit it yourself:** `python scripts/clean_data.py` rebuilds the table and
> rewrites the report; `python scripts/clean_data.py --verify` re-asserts that
> zero impossible values remain (exit code 1 if any check fails).

## Source data

Three CSVs scraped from [coachcox.co.uk/imstats](https://www.coachcox.co.uk/imstats/):

```
series.csv (69 rows)  ──id ← seriesID──►  races.csv (587)  ──id ← raceID──►  results.csv (~1.1M)
```

Ironman **140.6** (full-distance) results, **2002–2024**. Referential integrity
is perfect (0 orphan `raceID`s, 0 orphan `seriesID`s).

**Population framing — this matters for how percentiles are read.** The dataset
is the *regular Ironman circuit* and deliberately **excludes the Kona World
Championship** (the qualify-only global-elite event). So a percentile here means
"faster than people who **finished an Ironman**" — a fit but *attainable* peer
group — not "faster than the qualified elite." This is the honest comparison the
product wants. (The one World-Championship race that *is* in the raw data, St
George 2021, is removed — see Rule 2.)

## The cleaning rules

Rules run as an **attributable waterfall**: each rule's count is the rows it
removes from those that survived all *prior* rules, so the totals reconcile
exactly and nothing is double-counted.

| Step | Rule | Rows removed¹ | Why |
|---|---|---|---|
| pre | Drop non-finishers (DNS/DNF/DQ/NC) | 204,012 | The product ranks *finish performance*. Non-finishers have partial/no splits **by definition**, not by error — a DNF who quit on the bike legitimately has no run time. |
| 1 | Drop finishers with missing or out-of-bounds overall time | 2,602 | A "finisher" with no overall time is a broken/ghost record. Bounds: 7 h–19 h (faster than the world best, or past every race cutoff, = error). |
| 2 | Exclude St George World Championship (`seriesID = 330`) | 2,259 | Keeps the "regular circuit, no World Champs" population pure. It's a qualifier-only elite field (median finish 13.4 h) that would skew comparisons. ~0.25% of finishers. |
| 3 | Drop rows where `overall < swim + bike + run` | 873 | Physically impossible — you cannot finish in less than the sum of your own splits. (60 s slack allowed for rounding.) |
| 4 | De-duplicate `(raceID, athleteID)` | 205 | Same athlete should appear once per race. Keeps the most complete row (fewest NULL splits), lowest overall time as tiebreak. |

¹ Pulled from `cleaning_report.json`. Reconciliation:
892,707 finishers − 2,602 − 2,259 − 873 − 205 = **886,768 kept**.

### Per-segment outliers — NULLed, not dropped

Out-of-bounds **split** times are set to `NULL` while the rest of the row is
kept, so a finisher with one bad split still counts toward percentiles for their
*valid* segments and their overall time.

| Segment | Plausible range | Segments NULLed¹ | Why the bound |
|---|---|---|---|
| Swim (3.8 km) | 30 min – 2 h 20 | 7,195 | See swim note below. |
| Bike (180 km) | 3 h 30 – 10 h | 850 | Sub-3h30 is faster than pro pace; >10 h is past cutoff. |
| Run (42.2 km) | 2 h 15 – 8 h 20 | 2,159 | Slow outliers are usually the overall time mis-recorded in the run field. |

**Result:** kept-segment coverage is swim **96.8%**, bike **99.4%**, run
**99.4%**, and **97.9%** of kept finishers are in a standard age-group cohort.

#### Why a 30-minute swim *floor* (the interesting one)

A naive "drop swims faster than X% of the field median" rule was **rejected**.
The EDA found entire races with a legitimately fast field — e.g. race 457 has a
*median* swim of 9.8 min across 685 swimmers. Those are **current-assisted /
shortened swims** (downstream or tide-aided courses): the timing is real, but
it is **not a comparable 3.8 km effort**. A relative rule would keep them; they
should go.

So we use an **absolute physiological floor (30 min)**: below that it isn't a
real full-distance swim, whether from a shortened course or a dropped leading
digit in the source (`1:16:02` → `16:02`). This removes ~0.8% of swim values and
treats current-assisted swims as "not measured," which is the honest call.

## Time parsing

Raw times are strings in mixed formats: `MM:SS` (one colon) or `H:MM:SS` /
`HH:MM:SS` (two). They are parsed to **integer seconds**. The one-colon case is
ambiguous — `16:02` could be 16 min 2 s or 16 h 2 m. The EDA settled it: parsed
as `MM:SS`, 91% of one-colon values land in the plausible range; parsed as
`H:MM`, 0% do. So one colon = `MM:SS`. A consistency check confirms parsing is
correct end-to-end: `median(overall − (swim+bike+run)) = 14.5 min`, exactly the
expected T1+T2 transition time.

## Data dictionary — `clean_results`

| Column | Type | Meaning |
|---|---|---|
| `raceID` | VARCHAR | FK → `races.id`. The specific race instance. |
| `seriesID` | BIGINT | FK → `series.id`. The race series (e.g. Ironman Arizona). |
| `year` | BIGINT | Race year (2002–2024). |
| `series_name` | VARCHAR | Human-readable series name. |
| `continent` | VARCHAR | Continent of the series. |
| `athleteID` | VARCHAR | Athlete identifier (nullable in source for ~7% of rows). |
| `name` | VARCHAR | Athlete name. |
| `country` | VARCHAR | Athlete country. |
| `gender` | VARCHAR | `Male` / `Female` (266 raw `None`s dropped from gendered cohorts at query time). |
| `division` | VARCHAR | Raw division, e.g. `M40-44`, `FPRO`. |
| `is_age_group` | BOOLEAN | True for standard age-group divisions (`^[MF]\d\d-\d\d$`); excludes RELAY/PARA/bare M-F. |
| `is_pro` | BOOLEAN | True for `MPRO`/`FPRO`/`PRO`. |
| `overall_seconds` | INTEGER | Finish time in seconds. Always present and in-bounds (guaranteed by Rule 1). |
| `swim_seconds` | INTEGER | Swim split in seconds, or `NULL` if missing/out-of-bounds. |
| `bike_seconds` | INTEGER | Bike split in seconds, or `NULL`. |
| `run_seconds` | INTEGER | Run split in seconds, or `NULL`. |
| `overall_rank` | VARCHAR | Overall finish rank as recorded in source (kept verbatim). |
| `division_rank` | VARCHAR | Rank within division as recorded in source. |

> Note: `raceID`, `athleteID`, and the rank columns are carried as `VARCHAR`
> because the raw results file is read with `all_varchar=true` to take full
> control of time parsing. They can be cast at query time where numeric ordering
> is needed.

## Reproduce / verify

```bash
# Rebuild clean_results + regenerate cleaning_report.json (and auto-verify)
python scripts/clean_data.py

# Re-assert invariants on the existing table (CI-friendly; exit 1 on failure)
python scripts/clean_data.py --verify

# Keep the St George WC race instead of excluding it
python scripts/clean_data.py --keep-stgeorge
```

The verifier checks: every kept split is in-bounds, every overall is in-bounds,
`overall ≥ sum(splits)`, no St George rows, every kept row is a finisher, and
`(raceID, athleteID)` is unique.
